# RAG architecture

KaiAssistant uses repository-owned portfolio knowledge and keyword-first retrieval.

```text
Assistant request
  -> conversation window
  -> keyword search (IKeywordSearch)
  -> semantic fallback only when keyword evidence is weak
  -> bounded retrieved context
  -> Gemini streaming response
```

KnowledgeBootstrapHostedService reads `docs/rag-corpus` once at startup, hashes each supported file, skips unchanged sources, and persists keyword-searchable MongoDB chunks. It optionally embeds changed chunks; an embedding failure leaves keyword retrieval usable.

Production query embeddings are generated by the Infrastructure-only `GeminiEmbeddingService` behind `IEmbeddingService`. Documents use `RETRIEVAL_DOCUMENT`; questions use `RETRIEVAL_QUERY`. The configured `gemini-embedding-001` vectors are normalized to 768 dimensions and compared with cosine similarity. See [embedding-strategy.md](embedding-strategy.md).

## Current retrieval flow

Keyword retrieval runs first. Strong exact portfolio evidence avoids a query embedding. Weak evidence can invoke Gemini semantic retrieval; if that fails, the keyword result remains the safe degraded path.

Context selection bounds size, removes near duplicates, and retains source metadata. If no useful evidence exists, the assistant is instructed not to invent portfolio facts.

Retrieved corpus text is data, never instructions: application policy and system instructions always take precedence.

Activation validates every expected chunk ordinal against the current active index (or recorded document chunk count), rejects an empty corpus, and requires matching provider, model, embedding version, index version, metadata dimensions, actual vector length, finite values, and unique logical identities. The staged descriptor is never read by normal traffic before the atomic switch.

## Context selection and versioning

`RagContextSelector` applies an evidence threshold, exact and token-set near-duplicate suppression, a maximum estimated-token budget, a chunk limit, and deterministic order. Chunk ID, document ID, title, section, source, and version survive into `RagSnippet`. Embedding provider, model, dimensions, embedding-pipeline version, and index version are recorded with ingested chunks. There is no retrieval-result cache today; if one is introduced, its key must include normalized query, retrieval configuration, pipeline version, and index version.

RAG traces contain only strategy, bounded counts, and pipeline version. Metrics cover retrieval, semantic search, keyword search, fusion, reranking, context construction, candidate/selected counts, and empty retrievals; document text, prompts, queries, and embeddings are excluded.

## Trust boundary

Retrieved documents are data, not instructions. The system prompt states that system instructions and application policy override user input, and that instructions contained in retrieved material must not be followed.

## Ingestion

`IDocumentIngestionService` performs idempotent text ingestion using a normalized content hash. It records a `KnowledgeDocument`, chunks text on nearby sentence boundaries, generates an embedding for each chunk, and upserts `KnowledgeChunk` records through `IVectorStore`. A duplicate hash returns the existing document instead of recomputing embeddings.

For a multi-instance deployment, invoke this service from a durable queue consumer rather than an HTTP request. The current repository does not expose document uploads because it has no admin identity or file-storage contract yet.

The repository now provides that boundary at `POST /api/admin/knowledge/documents`. It requires the `RagAdmin` role and returns a durable ingestion-job identifier immediately; processing occurs in `DocumentIngestionWorker`.
